# ⭐ **NDH Documentation vs Expressive Governance Boundary Spec v1.0**  
### *Formal Boundary Definition Between Documentation Governance and Expressive Governance*

---

## ⭐ 1 — Purpose  
This specification defines the **formal boundary** between:

- the **Documentation Governance Layer**, and  
- the **Expressive Governance Layer** (the NDH Expressive Suite Publication Envelope Governance Spine).

It ensures contributors understand **which rules apply where**, prevents **cross‑layer drift**, and maintains **trauma‑informed clarity** across NDH governance artifacts.

This spec is **external** to the Omnibus Suite and is **not integrated** into any Suite version.

---

## ⭐ 2 — Layer Definitions

### ⭐ 2.1 — Documentation Governance Layer  
The documentation layer governs:

- **public‑facing clarity**  
- **documentation stability**  
- **version lineage**  
- **ASCII/PNG/SVG rules**  
- **trauma‑informed UX**  
- **cross‑layer coherence**  

Artifacts in this layer include:

- **Documentation Governance Charter v1.1**  
- **Documentation Governance Omnibus Suite v1.2**  
- **Documentation Governance Omnibus Suite v1.3**  
- **future documentation‑layer expansions (v1.4+)**

Documentation governance is **non‑constitutional** and **non‑activating**.

---

### ⭐ 2.2 — Expressive Governance Layer  
The expressive layer governs:

- **expressive geometry**  
- **curvature stability**  
- **drift suppression**  
- **activation conditions**  
- **risk and mitigation logic**  
- **audit lineage**  
- **constitutional topology**

Artifacts in this layer include:

- **Governance Charter (Expressive)**  
- **Envelope Spec**  
- **Safeguard Catalogue**  
- **Activation Protocol**  
- **Risk Register**  
- **Mitigation Playbook**  
- **Stability Matrix**  
- **Continuity Plan**  
- **Change Log / Ledger**  
- **Audit Log / Ledger**  
- **Backfilling Addendum**

Expressive governance is **constitutional**, **activating**, and **lifetime‑binding**.

---

## ⭐ 3 — Boundary Rules  
These rules define the separation between the two layers.

### ⭐ 3.1 — Documentation Cannot Govern Expressive Geometry  
Documentation governance **cannot**:

- define expressive geometry  
- modify curvature rules  
- alter drift suppression logic  
- participate in safeguard activation  
- bind into risk registers  
- influence stability matrices  
- propagate into continuity plans  
- enter audit lineage  
- trigger backfilling addenda  

These functions belong exclusively to the **Expressive Governance Spine**.

---

### ⭐ 3.2 — Expressive Governance Cannot Govern Documentation UX  
Expressive governance **cannot**:

- define ASCII rules  
- define PNG/SVG rules  
- define trauma‑informed UX  
- define public‑facing documentation structure  
- define contributor‑facing clarity rules  
- modify documentation lineage  
- override documentation stability envelopes  

These functions belong exclusively to the **Documentation Governance Layer**.

---

### ⭐ 3.3 — No Bidirectional Inheritance  
Documentation governance is **upstream** of expressive geometry only in the sense of:

- tone  
- accessibility  
- trauma‑informed boundaries  
- public‑facing clarity  

Expressive governance is **downstream** only in the sense of:

- internal geometry  
- curvature stability  
- safeguard activation  
- constitutional topology  

There is **no bidirectional inheritance**.

---

## ⭐ 4 — Interaction Rules  
These rules define how the layers may interact without crossing boundaries.

### ⭐ 4.1 — Shared Elements  
The layers may share:

- governance tone  
- provenance style  
- ASCII conceptual diagrams  
- versioning discipline  

These are **non‑binding** and **non‑constitutional**.

---

### ⭐ 4.2 — Interaction Layer  
The layers may interact through:

- **cross‑layer coherence clarifications**  
- **public‑facing explanations**  
- **documentation‑safe diagrams**  

But they may **not** interact through:

- activation logic  
- safeguard triggers  
- risk propagation  
- audit lineage  
- constitutional updates
