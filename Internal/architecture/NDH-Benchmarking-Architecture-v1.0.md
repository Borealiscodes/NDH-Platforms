# ⭐ 3 — Benchmarking Pipeline (Five Stages)

NDH benchmarking follows a **five‑stage pipeline**:

1. **Artifact Selection**  
2. **Benchmark Definition**  
3. **Evaluation Execution**  
4. **Signal Aggregation**  
5. **Benchmark Report Generation**

Each stage is described below.

---

## ⭐ Stage 1 — Artifact Selection

Artifacts eligible for benchmarking:

- internal reports  
- public reports  
- companions  
- diagrams  
- governance documents  
- telemetry schemas  
- search engine configurations  
- repo governance rules  

Artifacts *not* benchmarked:

- raw telemetry  
- internal governance signals  
- internal invariants  
- NDH manifold semantics  

These are evaluated indirectly via GQL.

---

## ⭐ Stage 2 — Benchmark Definition

Benchmarks are defined using NDH’s **Benchmark Definition Schema**:

- `benchmark_id`  
- `artifact_type`  
- `dimension` (quality/governance/system)  
- `criteria`  
- `thresholds`  
- `evaluation_method`  
- `expected_behavior`  
- `epistemic_lens` (optional)  

Benchmarks must be:

- deterministic  
- reproducible  
- non‑biased  
- epistemically inclusive  
- safe for public artifacts  
- strict for internal artifacts  

---

## ⭐ Stage 3 — Evaluation Execution

Evaluation methods include:

- structural analysis  
- semantic analysis  
- governance alignment checks  
- search engine retrieval tests  
- boundary safety tests  
- versioning discipline checks  
- provenance validation  
- diagrammatic consistency checks  
- epistemic lens neutrality checks  

Internal artifacts use **strict evaluation**.  
Public artifacts use **inclusive evaluation**.

---

## ⭐ Stage 4 — Signal Aggregation

Benchmark results are aggregated into **Benchmark State Objects**:

- `state_id`  
- `artifact_id`  
- `dimension`  
- `score`  
- `threshold_passed`  
- `issues`  
- `recommendations`  
- `timestamp`  

These objects are:

- internal only  
- indexed by the developer‑grade search engine  
- consumed by internal reports  
- never exposed publicly  

---

## ⭐ Stage 5 — Benchmark Report Generation

Benchmark reports come in two forms:

### **Internal Benchmark Report**
Contains:

- raw benchmark signals  
- detailed issues  
- governance alignment analysis  
- search engine indexing analysis  
- repo governance discipline analysis  

### **Public Benchmark Summary**
Contains:

- conceptual explanations  
- diagrams  
- high‑level insights  
- safety‑checked narrative  

Generated via:

- **Emergent Case Study (Public)**  
- **Meta Analysis (Public)**  

---

# ⭐ 4 — Integration with NDH Governance Layers

Benchmarking interacts with all layers:

- **Telemetry:** indirectly via GQL  
- **GQL:** consumes governance signals  
- **Internal Reports:** consume benchmark state  
- **Public Reports:** consume sanitized summaries  
- **Search Engines:** index benchmark metadata  
- **Repo Governance:** enforces benchmark placement  

This makes benchmarking a **cross‑layer architecture**.
