# ⭐ 2 — The Two NDH Search Engines

NDH requires **two** search engines, each serving a different audience and purpose.

---

## 🌿 **A. Accessible Search Engine (Public‑Safe)**  
### Purpose  
Provide conceptual, gentle, inclusive access to NDH knowledge.

### Characteristics  
- conversational  
- lens‑aware  
- supports Nye, Attenborough, Zen, Snek modes  
- avoids NDH manifold mechanics  
- avoids GQL internals  
- avoids raw telemetry  
- suggests epistemic lenses **non‑bias‑fully**  
- supports accessibility and expressive framing  

### Indexes  
- public reports  
- public companions  
- public diagrams/models  
- public case studies  
- public glossaries  
- public FAQs  
- public ethics/philosophy companions  
- public AI‑Zen and accessibility/snek companions  

### Does NOT index  
- raw telemetry  
- GQL internals  
- NDH invariants  
- internal companions  
- ops artifacts  
- NDH manifold semantics  

---

## 🧠 **B. Developer‑Grade Search Engine (Internal)**  
### Purpose  
Provide structured, schema‑aware access to NDH’s internal knowledge architecture.

### Characteristics  
- developer‑grade  
- schema‑aware  
- GQL‑aligned  
- governance‑layer aware  
- supports manifold, invariants, telemetry  
- returns internal artifacts directly  
- supports ops workflows  
- supports NDH governance math  
- supports architectural reasoning  

### Indexes  
- internal reports  
- internal companions  
- ops artifacts  
- GQL Processing Specification  
- Raw Dataset Population Plan  
- Repo Integration Checklist  
- NDH manifold semantics  
- telemetry schemas  
- invariants  
- governance math  
- internal diagrams/models  

### Does NOT index  
- public‑only artifacts  
- sanitized versions  
- conceptual summaries  
- accessibility/snek companions (unless internal variant exists)

# ⭐ 3 — Unified Indexing Schema

Both search engines rely on the same **registry** and **taxonomy**, but apply different filters.

### Core Schema Fields  
Each artifact must declare:

- **type** — report, companion, ops artifact  
- **scope** — internal, public, dual  
- **lens** — epistemic lens  
- **layer** — telemetry, GQL, internal, public, search, repo  
- **path** — repo file path  
- **version** — semantic version  
- **provenance** — raw or sanitized  
- **citations** — internal or public  
- **safety** — publication constraints  

This schema prevents drift and ensures consistent indexing.

# ⭐ 4 — Epistemic Lens Engine

NDH supports multiple epistemic lenses:

- scientific  
- engineering  
- mathematical  
- philosophical  
- ethical  
- artistic  
- esoteric  
- cognitive  
- trauma‑informed  
- accessibility/snek  
- AI‑Zen  

### Lens Selection Rules  
> NDH may suggest lenses, but suggestions must remain non‑directive, non‑biased, and non‑prescriptive.  
> Users retain full agency over interpretive frameworks.  
> Some users require highly specialized or esoteric lenses; NDH must support these without privileging any worldview.

The Accessible Search Engine uses this heavily.  
The Developer‑Grade Search Engine uses it lightly.

# ⭐ 5 — GQL Integration Model

GQL interacts with the search engines via:

### **Internal Engine**
- indexes GQL outputs  
- indexes GQL specs  
- indexes telemetry schemas  
- indexes governance math  
- indexes invariants  

### **Accessible Engine**
- indexes public summaries of GQL behavior  
- indexes conceptual diagrams  
- indexes public governance explanations  

GQL never exposes raw telemetry or internal mechanics to the public engine.

Search engines rely on:

- file paths

- commit descriptions  
- provenance/citation footers  
- artifact lifecycle rules  
- internal/public placement  

This ensures:

- no leakage  
- no drift  
- no holonomy  
- no envelope breach
