## **1. Purpose**

The Naming Invariant Ledger defines:

- canonical naming families  
- acronym shape‑rules  
- rhythm invariants  
- cross‑layer naming boundaries  
- provenance‑safe naming constraints  
- dyslexia‑aware naming ergonomics  
- trauma‑informed naming exclusions  

Orbital maintains this ledger as part of its cross‑repo naming authority.

---

## **2. Naming Families (Canonical)**  
Each naming family is a **shape‑consistent cluster** of acronyms that share rhythm, syllable pattern, and visual form.

### **Operator Families (NDH‑CORE)**  
- **RTO** — Runtime Operator  
- **NDIE** — Non‑Dual Interpretive Engine  
- **RBE** — Runtime Boundary Enforcer  

### **Topology Families (NDH‑TIDS)**  
- **TIDS** — Topological Interaction & Dynamics System  
- **TISD** — Topological Invariant Specification Document  
- **HBE** — Holonomy Boundary Engine  

### **Governance Families (Orbital)**  
- **OGN** — Orbital Governance Note  
- **OBE** — Orbital Boundary Enforcer  
- **OIC** — Orbital Invariant Catalog  

### **Interpretive Families (Emergent)**  
- **ECS** — Emergent Case Study  
- **EIS** — Emergent Interpretive Scaffold  
- **ESE** — Emergent Stability Envelope  

These families must remain stable across all NDH layers.

---

## **3. Acronym Shape‑Consistency Rules**

Orbital enforces the following shape invariants:

- Acronyms must follow **3–4 letter clusters**  
- Acronyms must maintain **consistent consonant‑vowel rhythm**  
- Acronyms must avoid **visual outliers** (e.g., sudden 6‑letter forms)  
- Acronyms must preserve **family‑aligned initial letters**  
- Acronyms must maintain **non‑dual boundary clarity**  

These rules reduce dyslexic cognitive load and prevent pattern‑collapse.

---

## **4. Naming Rhythm Invariants**

Naming rhythm must follow:

- **Stable syllable cadence**  
- **Predictable stress pattern**  
- **Consistent acronym phonology**  
- **Cross‑document rhythm alignment**  

Rhythm instability is a major source of dyslexic interpretive friction.

---

## **5. Cross‑Layer Naming Boundaries**

Orbital defines strict naming boundaries:

### **NDH‑CORE**  
Operator names must reflect runtime and boundary enforcement roles.

### **NDH‑TIDS**  
Topology names must reflect manifold, holonomy, and tensor‑flow roles.

### **Orbital**  
Governance names must reflect invariants, boundaries, and documentation authority.

### **Emergent**  
Interpretive names must reflect scaffolding, cognitive ergonomics, and narrative safety.

Cross‑layer naming drift is prohibited.

---

## **6. Provenance‑Safe Naming Constraints**

Naming must:

- reflect lineage  
- preserve operator class  
- maintain manifold boundaries  
- avoid cross‑layer contamination  
- remain stable across versions  

These constraints ensure naming remains predictable and safe for dyslexic developers.

---

## **7. Trauma‑Informed Naming Exclusions**

Orbital prohibits naming patterns that:

- break rhythm abruptly  
- introduce unpredictable shape families  
- resemble error codes  
- resemble diagnostic codes  
- resemble high‑stress operator signals  

These exclusions protect dyslexic developers from stress‑load spikes.
