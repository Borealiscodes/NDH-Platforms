# ⭐ **VM 2.0 Criteria Document — NDH‑Orbital‑GQL Virtual Machine**  
### *Formal Criteria for Next‑Generation VM Evolution*  
### **Version:** 2.0‑Criteria

---

## ⭐ **Concise Takeaway**  
VM 2.0 is **not** a feature upgrade — it is a *paradigm shift*.  
It is only justified when NDH requires:

- a new execution model,  
- a new ISA class,  
- a new safety envelope,  
- or a new transmission spine architecture.

VM 2.0 is triggered only when **all** VM 1.1 capabilities are insufficient.

---

# **1. Purpose of This Document**

This document defines the **formal criteria** for when NDH may evolve the Orbital‑GQL Virtual Machine from **v1.1 → v2.0**.

It ensures:

- no premature VM evolution  
- no ISA drift  
- no governance collisions  
- no trauma‑unsafe runtime changes  
- no TISD contamination  
- no Hyperatlas routing instability  
- no collapse of the NDH Consolidation Spine  

VM 2.0 must be **earned**, not assumed.

---

# **2. VM 2.0 Trigger Conditions**

VM 2.0 is justified only when **all** of the following conditions are met.

---

## **Condition A — ISA Expansion Beyond Soft‑Boundary Primitives**

VM 2.0 requires:

- expressive‑stability ISA  
- curvature‑native instructions  
- holonomy‑native instructions  
- provenance‑native instructions  
- Hyperatlas‑native routing instructions  
- Simulation‑Suite execution instructions  

If NDH needs instructions that **cannot** be expressed in VM 1.1’s ISA, VM 2.0 is triggered.

---

## **Condition B — Memory Model Evolution**

VM 2.0 requires:

- multi‑layer stability memory  
- holonomy envelope memory  
- curvature basin memory  
- transmission‑spine routing memory  
- multi‑tenant governance memory  

If NDH needs memory regions that **cannot** be represented in VM 1.1’s deterministic model, VM 2.0 is triggered.

---

## **Condition C — New Execution Paradigm**

VM 2.0 is justified when NDH requires:

- long‑lived governance fibers  
- streaming governance processes  
- multi‑tenant orbital execution  
- continuous provenance monitoring  
- real‑time Hyperatlas routing  

If NDH needs execution semantics beyond VM 1.1’s deterministic envelope, VM 2.0 is triggered.

---

## **Condition D — New Safety Envelope**

VM 2.0 requires:

- Sentinel Network v2.0  
- trauma‑safe multi‑tenant boundaries  
- recursion‑safe orbital fibers  
- provenance‑safe streaming  
- non‑dual execution primitives  

If NDH needs a safety envelope that **cannot** be enforced by VM 1.1’s sandbox, VM 2.0 is triggered.

---

## **Condition E — Transmission Spine Evolution**

VM 2.0 is justified when:

- the NDH Consolidation Spine becomes VM‑native  
- routing must occur inside the VM  
- provenance must be enforced inside the VM  
- stability geometry must be executed inside the VM  
- tonal geometry must be resolved inside the VM  

If the transmission spine must be **internal** rather than **external**, VM 2.0 is triggered.

---

# **3. VM 2.0 Prohibited Triggers**

VM 2.0 **must not** be triggered by:

- IDE hook migration  
- governance automation  
- naming‑family expansion  
- provenance schema updates  
- TISD supersession logic  
- Simulation‑Suite tooling pressure  
- Stability‑Manifold clay expansion  
- Tonal‑Geometry documentation growth  

These are **not** sufficient reasons.
